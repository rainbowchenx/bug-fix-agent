# Agent3 真实项目评测方法

记录日期：2026-11-15（Asia/Shanghai）。用于首次业务实测及后续版本对照；不是已完成的评测结果。

关联：[修订方案](../../superpowers/specs/2026-11-15-agent3-repair-feedback-design.md) · [实施计划](../../superpowers/plans/2026-11-15-agent3-repair-feedback-implementation-plan.md) · [逐票评审表](templates/ticket-review.md) · [逐票汇总表 CSV](templates/ticket-review-summary.csv) · [批次报告模板](templates/batch-evaluation-report.md)。

## 明天的使用顺序

1. 在仓外业务产物目录复制模板，填写批次配置。模板可入版本库，原始业务工单、日志和代码依照项目要求保存在受控目录，不直接放回本仓。
2. 选取建议15—25张代表性缺陷；人力不足可缩小，报告实际数量。规模仅为操作建议，不代表统计显著性。优先连续近期票，再补特殊场景，保存纳入/排除原因。
3. 固定输入、代码和运行配置，原样完成第一轮。每票填写汇总CSV，深度评审使用逐票Markdown；所有输入票都保留行。
4. 审阅并选择补丁，在正确基线自行应用，执行适用检查和业务验收。记录人工改动与耗时。
5. 至少挑选缺信息补充、拒绝后纠正、已应用后追加三类票，验证二次修复；补充和修改均作为新轮次保存。
6. 按批次模板统计结果、列出案例和改进优先级。缺少真值的项填“无法判断”，没有验收的填“未验收”。

## 样本与运行条件

样本覆盖：清晰可修票、模糊/缺图/缺日志票、疑似仓外票、依赖专用环境票、需要再次修复票；类别允许重叠。不得只挑容易成功的票，失败和运行中断不得从分母删除。

历史已修复票可作为参照，必须使用修复前代码，不向Agent3暴露最终补丁。人工修复是参考实现之一，不能要求文件或diff完全一致。已知修复若进入Agent2、文档、会话等输入，标注答案泄露，不与盲测混算。

每轮记录Agent3 commit、工作区dirty、模型、SDK/CLI版本、实际轮次/时间/token预算、仓库HEAD及内容状态、原始票、Agent1/2产物摘要、业务skill版本、可用工具与环境。多仓分别记录。用户测试构建应关联源码或注明未知。

## 四层评判

| 层次 | 检查 | 结果 |
|---|---|---|
| 理解 | 现象、预期、条件是否准确，冲突是否发现 | 正确/部分正确/错误/无法判断 |
| 分析 | 路径和因果机制是否有可核查依据，有无编造 | 有依据/合理待证/错误/无法判断 |
| 补丁 | 完整可应用、针对机制、范围适当、无明显副作用 | 可接受/需人工修改/拒绝/待验证/无补丁 |
| 验收 | 实际应用后目标与相邻场景的表现 | 解决/部分解决/未解决/引入回归/未验收 |

编译通过不等于缺陷解决；合理静态分析不等于实机验证。不要照抄Agent3自评作为人工评分。审阅者应给出代码、日志、截图或实际操作依据；未掌握业务事实时明确无法判断。

无补丁票也评审：阻断正确性、已完成调查价值、补充请求是否具体有效、是否提前退回。外部归属、疑似外部、尚未定位必须区分；缺图不自动等于无法修复。

## 人工介入与反馈

接受程度采用：原样接受、机械调整、人工逻辑修改、仅分析有用、全部无帮助、未评审。机械调整只包含不改变逻辑的应用冲突等；记录具体变化。未经逻辑修改原样应用的票，与人工辅助后成功的票分别统计，不重复计为Agent3原样解决。

记录审阅、应用调整、人工逻辑修改、业务验收耗时；与Agent运行耗时分别展示。耗时可估算，但需标记估算。实际反馈关联票、attempt、补丁、代码/构建、应用状态和新增材料。

二次修复检查：吸收新事实、撤销错误假设、确认实际补丁状态、复用有效调查、新补丁前提正确、得到可核实进展。不是仅看是否再次生成补丁。一个缺陷多个attempt在总体分母只计一票；轮次成本累计，单独展示首次与最终结果。

## 统计口径

统一以“项目命名空间+源缺陷ID”为票身份；重复导入单独登记输入项数量，但唯一缺陷只计一次。每票选定本次评测的候选/attempt，另保留历史。以下分母都注明实际n，零分母填N/A；未评审、未应用、未验收分别展示，不能归为成功。

| 指标 | 分子/分母 |
|---|---|
| 报告覆盖 | 有明确处理去向的唯一票/全部输入唯一票 |
| 候选产出 | 至少产出过候选的唯一票/全部输入唯一票；另列当前有效候选 |
| 事实错误 | 已核实存在严重事实错误的票数/已完成人工事实评审票数；附明细 |
| 补丁可应用 | 选定完整候选成功应用的票/实际尝试应用该候选的票 |
| 原样接受 | 无需人工逻辑修改而接受的票/已审阅候选票；机械调整单列 |
| 原样解决 | 原样或仅机械调整后验收解决的票/该组已业务验收票；严格零调整数量另列 |
| 人工辅助解决 | 人工逻辑修改后解决的票/该组已业务验收票，不并入原样解决 |
| 验收覆盖 | 已业务验收候选票/已应用候选票；应用前发现错误的拒绝票另列 |
| 回归 | 观察到新增问题的票/已进行相关回归验收票；明确所测范围 |
| 阻断质量 | 人工确认判断正确且请求有效的票/已核查阻断票 |
| 二次推进 | 补充后取得有证据进展的票/实际再次执行的票；另列最终解决数 |
| 成本 | 每票运行和人工耗时、token、费用的样本数、中位数、范围及总量 |

结果是当前样本上的描述性统计，不外推总体成功率。用户只挑选喜欢的补丁应用，会导致验收样本偏向较好候选；必须同时展示拒绝数和验收覆盖。相较历史工具的节省时间只有可比记录时才声称，不能凭感觉计算节省百分比。

## 归因与报告

每票可多选：原始资料、Agent1保真/预期/筛选、Agent2定位/事实/覆盖、Agent3分析、Agent3编辑、验证交付、环境/外部依赖、无法归因。上游错误与Agent3未纠正可同时记录，不能只追究最早环节。所有归因附证据，模型输出不是独立真值。

批次报告必须同时呈现全部票、已审阅候选、已应用和已验收这几个规模。选择至少一张成功、一张失败和一张二次修复案例，串起原票→上游→分析→补丁→人工介入→验证。

后续版本对照使用相同输入、代码、环境和尽量一致的模型预算；变化项明确列出。Agent2收益区分调查节省和最终修复效果，可先人工审阅轨迹，再做受控对照。首次实测目标是建立可信基线，不预设成功率阈值。
