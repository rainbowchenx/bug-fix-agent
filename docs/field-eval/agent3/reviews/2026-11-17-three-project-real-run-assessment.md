### 4.1 16票调度上限解除了，但不能据此认定有效调查已覆盖

三线93票都进入了分组调用。HCP确实从一次最多16票变成5组覆盖37票，工程调度有正向进展。但12个可解析组全部出现 `dropped=invalid_match:<组票数>`，合85次；最终facts和searchedScopes均为空。

代表：HCP第一组detail为 `turns=69; reason=completed; cost=$5.06; dropped=invalid_match:8`。`_coerce_sdk_match` 会把无法通过DefectCodeMatch的条目整体丢弃；调用方保留baseline并按原始返回ID更新覆盖状态。因而能同时出现“模型completed”“条目丢弃”“最终partial”。

准确结论是**85次条目级schema拒绝、没有交付结构化逐票调查证据**。由于未保留原始SDK返回和具体ValidationError，不能把85直接当85个唯一原始响应ID，也不能断言是facts字段、source枚举或其它某一字段导致。顶层“只是模型没填facts/scopes”证据不足。

最终候选的why仍为 `exact basename`、`package/dir`、`weak basename substring` 等规则命中。例如HCP04123/04635均给resourceAppManagement的通用loading文件；A3随后排除并另找HotSpare/LinkageConfigForm。候选source=grep本身不能证明模型逐票读过源码。架构增强可能仍有价值，但不能替代被丢弃的调查交接。

### 4.2 状态和成本不应误读

实际状态为85 partial、4 search_draft、4 not_investigated，共93，不是“所有原始票全部partial”。交通第三组8票返回 `sdk returned no parseable JSON cartography`，其中4票有规则草案、4票无候选。它们确实进入过调用，因此单看not_investigated不能区分“从未启动”和“调用后失败”；需要结合investigationRuns。

该失败组是9398/6318所在组；Agent3解析失败的却是0935/2247。不能直接把两张A3失败归因为同一A2失败组。

包中记录的695 turns/$43.76只覆盖可读SDK估算记录，不是实际结算费用；失败组缺金额，且没有Agent3独立账单。旧包三线可读A2金额为$16.12，调用覆盖范围也不同，不能直接比较单票修复成本。当前更不能认定有效调查的成本效率提高。

缓存只复用complete组，本批没有complete。即使配置了缓存，也不能宣称本批已验证有效复用/失败续跑；当前材料无同配置二次续跑案例。

三线 `02-agent2/run.log` 第1条警告均明确：allowed_tools整项允许Bash等工具，会使 `can_use_tool` 不被调用；SDK提示改用PreToolUse hook或收窄allow规则。
