## §2 新指标：①-a 97.8% 到底证明了什么

把「单子里出现**基线代码里原样存在**的中文字符串」当作**有实体锚点**的充分条件（长度 ≥6 字、且该串在基线出现 ≤12 处才计入），对 319 条全跑：

```
基线可用锚点：13 / 319 = 4.1%
```

命中的 13 条长这样（都是**原样引用了 UI 文案**）：

| 缺陷 | 锚点串 | 基线落点 |
|---|---|---|
| BGCM2026051103143 | 切换至自动分区配置模式 | `web/src/i18n/zh_CN/projectDetail.json:45` |
| BGCM2026051102234 | 切换至手动分区配置模式 | `projectDetail.json:44` |
| BGCM2026051400451 | 重新计算顶点 | `web/src/i18n/zh_CN/config.json:88` |
| BGCM2026052903370 | 获取进度失败 | `electron/…/selfCode.json:18` |
| BGCM2026051104101 | 请增加屏幕亮度或校正灰阶 | `calibration-subsystem/src/locale/zh_CN/algorithmSDK.json:77` |

**这意味着**：

- `①-a 97.8%` 的准确语义 = **「没被已知 8 类模式拦下」**（default 放行 98%），不是「我证明了这个单子能定位」。
- 真正能**机械锚定**到基线代码的只有 **4.1%**。其余 96% 要靠「业务词 → 模块」的语义映射，而这一步在 `_pipeline.md` 坑 13 里已经被证伪（hc 自动定位 top-1 = 0/6）。
- 这个 4.1% 是**下界**（不引用代码字符串也能定位的情况存在），但它是目前唯一**可复算、不含主观判断**的①-a 含量指标。

> 这正好回答了 `_stage1-rules.md` §已知缺陷 #1 和 #6：要变正向判定，就得要求「能从标题提取可映射到仓库的实体名」——LED 实测这个条件是 **4.1%**。

| **「翻译补充/样式修复」类聚簇** | 27 个提交都叫 `fix: 翻译补充` / `fix: 样式修复`，翻译类缺陷必命中其中之一但多半是**另一句**翻译 |

### 4.4 结论

```
S8 命中率        6/30 = 20.0%（95% CI ≈ 8%~39%）
误配率           22/30 = 73.3%
全量投影下界     20% × 85.6% ≈ 17%（约 54/319）
命中时的档位     6/6 全部落在 A 档
```

> **S8 只能当下界，且它找到的正是"改法本来就明确"的那批**。A 档 7 条里 S8 找到 5 条（召回 71%），A 档之外的 23 条 **0 命中**。
> 这与 hc 完全同构：hc 自动 9.5% vs 人工盲测 10%；LED 自动 20% vs 人工盲证 10%——**两个独立方法互相收敛在 10%~20% 这个量级**。

## §5 三问的最终答案

```
Q1 一次猜中真实改法   ≈ 10%~20%     ← n=30，CI 宽，别当精确值
Q2 给了代码能不能改   = 23.3%（A）/ 70.0%（A+B）
Q3 改完现象消不消失   = 未知
```

**为什么 Q2 高而 Q1 低**：Q2 允许我搜代码、看上下文、查业务事实；Q1 要求"缺陷单里的词"和"修复提交里的词"对上——而 LED 实测二者交集极小。

**三层损耗（每层都有实例）**：

| 层 | 现象 → 机制 | 实例 |
|---|---|---|
| ① 现象 → 机制 | 「任务名称虽提示不能为空但实际能保存」→ 实际改的是 `console.error` 里的文案？不是，改的是保存前校验 | 我按关键词搜到 2 个提交全是翻译/仿真，都不对 |
| ② 现象 → 文件 | 「分区配置-英文界面：过渡区提示未翻译」→ 命中的提交改的是「切换至手动配置分区模式」，**同一页面的另一句** | 4 条翻译单共享同一批提交 |
| ③ 修复 → 提交 | 一条提交修 N 条：`796e1635f2` 一条覆盖 6 条缺陷、`14e47596a2` 覆盖 4 条 | 45% 的命中提交是多目的提交 |
