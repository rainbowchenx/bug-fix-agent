## 0. 结论先行

> ### ⚠️ 口径更正（2026-10-29）：①「可修率」应读作「可定位率」
>
> `verdict.ts` 的 `FIXABLE` 只表示「信息够定位」，代码里 `expectation-empty` 历史上**只进 evidenceGaps、不影响判定**。
> 已新增正交字段 `expectQuality`（explicit / inferred / ambiguous / absent），严格可修 = `FIXABLE && expectQuality ∈ {explicit, inferred}`。
>
> **「期望存在」≠「期望唯一」**：标题「A 没有 B」能推出期望（存在），但「两端不一致」推不出改哪端（不唯一）。
>
> | 口径 | 本产品线 |
> |---|---|
> | ①-a 可定位（原报告的「可修」） | 185 / 200 = 92.5% |
> | **①-b 严格可修（期望唯一）** | **101 / 200 = 50.5%（参考值）** |
>
> 期望不唯一的主因（按条数）：方向不唯一（两端以谁为准）· 目标值不唯一（距边界几 px）· 基准不唯一（以 550/CS 端为准）· 资源不唯一（设计稿）。
> 规则判定为粗筛（hcp 校准 80% 召回），权威值仍以人工/抽样的 A 档为准。

## 5. 对本产品的含义

1. **「可修率」高不代表「能自动修」**：92.5% 是**信息充分度**，47% 只有功能点级定位。报告必须区分「信息充分」与「可定位到文件」。
2. **i18n 是这个业务组的稳定大头**（27 条，13.5%）：改法确定（补 key / 补翻译），是最值得自动化的类；但要警惕把「阿语下按钮溢出」这类**布局**问题误归 i18n。
3. **浏览器/插件类必须前置拦截**：5 条不可修里 4 条是「火狐/Mac 无插件」，产品设计如此。
4. **"建议类"要单独走**：#82（「免费试用路数不要写死，建议根据后台配置动态显示」）不是缺陷，是需求建议 → 归 `NOTCODE`/产品决策。
5. **未脱敏**：35 条含明文账号口令，会进 prompt 与报告 → 必须 scrub。
6. **`Closed` 占 83%**：这批适合做「输入形态 + 判定校准」，**不适合估真实吞吐/比例**。
