## 3. S8：首次做出，但只能当下界

### 3.1 方法

1. 20 个子仓各跑一次 `git log --since=2026-08-31 -p --unified=0 --no-merges`，抽「含中文的新增/删除行」建索引（397 提交 / 219 份中文 diff）
2. 缺陷标题 → 中文 3/4-gram（去虚词、去通用词、至少含 1 个实词）
3. 匹配条件（比 hcp 更严，因为 hc 的提交更碎）：
   - 提交日期 **≥ 缺陷创建日**（修复不能早于提单）
   - 命中 ≥2 个 gram，且至少 1 个 `df ≤ 5` 的稀有 gram
   - 排除大杂烩（文件 >6 或 ±行 >250）与非修复类 subject（refactor/style/注释/日志/合并/骨架屏/回退）
   - 一条提交若被 >3 条缺陷共享 → 视为「大提交」，不计高置信
4. 用 **idf 加权**排序（`log(1+N/(1+df))`）

| `所有监控点` | 4 处，全是**别的功能** | 关键词命中 ≠ 落点正确 |

**③ 修复 → 提交**（一条提交修 N 条）

hc 的批量修复极多：`cbe7cf9 fix 历史小语种缺陷修复优化`、`f4ad5551`（3 条导出）、`3086b24d`（10 条每日总结）。
所以「找不到 1:1 commit」有一半是**任务结构**造成的，不是判错了。

#### 必须承认的样本局限

- n=20，✅2 条的 95% 置信区间约 **1%~32%**，不能定论
- 7 条「未找到」里，至少 3 条（#6 枪支小类、#8 常量、#17 升级页英文）**很可能是我搜错了文件**——每条我只试了 1~2 个特征串
- 缺陷单只有 41.9%~69.5% 写了预期结果，且 83%~95% 与本缺陷无关 → **"改法唯一"这件事在输入端就不成立**

#### 结论

> **10% 不是「这套方法只能做 10%」，而是「一次成型、无环境、无补料、无追问」条件下，从现象直推机制的成功率。**
> 同一批缺陷在 hcp 上做 ② 判读时给出 65.4%，那是在**看到代码后判断"能不能改"**，不是"一次猜中真实改动"——**两者不是同一个问题**。
