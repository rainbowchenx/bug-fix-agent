## 0. 一句话

**输入 = 创建时刻的两个字段（标题 + 描述）；输出 = 每条的（可定位性 / 期望唯一性 / 类型 / 簇 / 定位档 / 置信度）。**
全程**排除法**：先剔已知不可判的，剩下的默认放行——**所以 `FIXABLE` 的语义是「没被已知模式拦下」，不是「我证明了能定位」**。

```
原始行
 ↓ S0 字段裁剪（A 组）     丢掉闭环字段 → 只留创建时刻信息
 ↓ S1 去重（A7）           标记不剔除，分母不变
 ↓ S2 生产者分流（C7）     SCA/CVE 扫描单 → UNFIXABLE
 ↓ S3 归属排除（C3/C3b）   非代码归属 → UNFIXABLE
 ↓ S4 期望未定义（C2）     需求变更/待拍板 → UNFIXABLE
 ↓ S5 运行时/附件（C4/C5） 崩溃无堆栈/依赖附件 → UNFIXABLE
 ↓ S6 不可断言（C1a~C1e）  空模板/纯形容词/无量化 → UNFIXABLE
 ↓ 默认放行                 verdict = FIXABLE
 ↓ S7 期望唯一性（正交）    explicit / inferred / ambiguous / absent
 ↓ S8 分簇（B 组）          标题前缀 或 模块标签
 ↓ S9 类型（E 组）          有序短路 11 类
 ↓ S10 定位档 + 置信度（D/F 组）
```

## S0 字段裁剪（A 组 · `fields.ts`）

**核心约束**：真实缺陷单是 `Open`/`New` 状态，闭环后才有值。凡闭环后才写进去的字段，一律禁用——**否则等于用答案判题**。

> **2026-10-29 重导出（hc-bug-1029，69 列）之后的修订**：平台可以把闭环字段全带出来（`解决结论` 100% / `解决方法` 88% / `验证结论` 90.3%）。
> 同一份文件里既有无答案的单，也有全是答案的单，**字段名单必须比数据更严**。
> **用户裁定（本版）**：
> - `引入活动` → **参考，不可作硬参照**（事后归因，但能解释「为何难」）
> - `所属项目编号` / `检出项目名称` → **保留为项目标识**，用于切开多项目混表；不参与可修性判定
> - `测试环境` → **复现场景**（环境名 + URL + 账号，可驱动 Playwright），**不脱敏**
> - `测试项` → **可选**，有值即测试用例（当前全空，不影响结论）
> - 人员冗余类（`申请人`/`发现人员`/`验证人员`/`申请人所属部门`/`关联流程ID`）→ **完全丢弃**
> - B 组闭环字段 → **确实禁用**
> - **★ `所属模块` → 完全不可用（关单时才填写）**，既不可作判定指标、也不可作分簇键、也不作事后核对。证据：
>   hc 实测 `Closed` 97.6% / `Solved` 100% vs **`Open` 18.8%（3/16）** / **`Cancel` 0%（0/4）**；
>   配套 `Cancel` 0%（0/7）；LED `Cancel` 0%（0/11）。且近似一对一绑定开发者（门禁/实时监控→同一人 9/9）。
>   → 连带：`LED_PROFILE.clusterFrom` 已从 `moduleTag` 改为 `titleTag`（LED 无 `测试模块` 列，创建时无法分簇）
> - 新增可用项：`测试模块`（100% / 52 种，97.3% 等于标题前缀，**比正则更准**）
>
> 详见 [`hc-缺陷表结构-1029.md`](hc-缺陷表结构-1029.md)。

## S2 生产者分流（C7）

```
SCANNER_RE.test(全文)  ← 检出工具|软件成分分析|静态检测|hikshield|漏洞名称  (可被 profile.scaSource 扩展)
  ├─ 且 CVE_RE 命中  ← CVE-\d|CVE漏洞  (可被 profile.scaVuln 扩展)
  │    → UNFIXABLE / reason=SCA
  └─ 未命中 CVE
       → FIXABLE（代码级安全配置能改，不下发依赖升级）
```

**为什么只命中扫描器不算不可修**：安全配置（CSP、ATS、cookie 属性）是业务代码能改的。

## S4 期望未定义（C2）

**只看 `sig = 标题 + 实际结果段`**（不用预期段），因为模板里的「校验是否有翻译」之类话术会误命中。

| 判据 | 结论 |
|---|---|
| 标题前缀 = `需求变更` | `UNFIXABLE / DESIGN` |
| `请保持一致\|需要保持一致` | `DESIGN`（两端不一致但未定基准） |
| `建议统一\|拍板\|找能拍板` | `DESIGN`（需业务拍板） |
| `(是否\|需确认\|确认是否)…(展示\|保留\|增加\|支持\|修改\|统一\|翻译)` | `DESIGN`（疑问句未定） |

**豁免**：`sig` 含 `基线|550` 时，「未定基准」类规则不生效——给了对照基准就不是「未定义」。

## S5 运行时 / 附件依赖（C4 / C5）

**C4 运行时依赖**（任一命中 → `RUNTIME`）：

```
崩溃/白屏 + 概率性词 + 正文无堆栈          ← 缺复现条件
老设备 | \d\.\d\.\d+ 老                  ← 依赖特定老设备
(三星|华为|小米|OPPO|vivo|Pixel|mate\d+) + (未复现|其他手机|其他机型)  ← 特定机型不复现
```

**C5 附件依赖**（→ `ATTACH`）：

```
看群里|群里发|没法上传|附件传不|附件上传失败
或 (附件|截图|录屏|视频|文件)…上传失败
或 上传失败…(附件|截图|录屏)
```

> **关键区分**：裸「上传失败」是**业务现象**（系数上传失败 = 缺陷本身），只有与附件/截图/录屏**同现**才是「附件不可得」。led 曾因裸「上传失败」误杀 2 条。

## S6 不可断言（C1a ~ C1e）

### C1a 空模板
区分「实际结果空」与「预期结果空」——**修的东西完全不同**。

| 状态 | 处置 |
|---|---|
| 模板占位（`包括复现方法和现象描述等`）或 实际结果段 <4 字 | 若 `profile.rejectEmptyTemplate` → `VAGUE`；否则**退回只看标题**并记 `evidenceGaps: description-empty` + 置信度封顶 `medium` |
| 预期结果段为空（`预期结果：` 后直接是 `实际结果`/`问题`/`建议`/空） | 记 `evidenceGaps: expectation-empty`，**不阻断判定** |

> 坑 7：空模板 ≠ 不可断言。hc 实测「实际结果空但标题自足」21/22 条，直接判死会误杀。
> 坑 11：`expectation-empty` 曾只记录不参与判定 → **已被 S7 修正**。

### C1b 崩溃无信息

| **锚点门** | `hasAnchor = URL \| IP \| 引号提示语 \| {} \| codeAnchors` | `#02047`「配置前端设备开启萤石云失败（**10.66.70.22**）」· `#03342`「异常原因为 **{}**」· `#06472`「提示“**找不到可恢复的执行记录**”」 |
| **期望门** | `expectQuality ∈ {explicit, inferred}` | `#04579`「配置设备分辨率失败」→ 预期段写清「下发成功、展示验收结果」，「失败」本身已是完整现象 |

**hitools 的批量形态**：`配置码率上限执行失败` / `配置视频帧率执行失败` / `配置码率类型执行失败`（各 9~13 字）。
对象明确 + 预期明确，**原规则靠「实际段 <15 字」把它们全杀了**。

**两层豁免**：
- 「该报错却没报」= 缺校验（`不报错|未拦截|未做校验`），不是报错信息不足
- **因果结构**（`导致|致使|造成|引起`）已给全链路，不是「只写报错」（led #1201223）

### 兜底
以上全过 → `fixed("default")` → `FIXABLE / reason=OK`（若命中 `问题1：…问题2：` 等多缺陷模式则 `reason=MULTI`，**但不影响 verdict**）。

> **实测：86~98% 的单子走 default**（hcp 151/159、hc 185/200、配套 171/200、led 312/319）。
> 这是本阶段最大的结构性弱点，见 §已知缺陷。

## C8 无锚点（`anchor.ts`，2026-10-29 新增）

**为什么加**：S2–S6 前 11 条判据全是**排除法**（文本自相矛盾才拦），实测：
1664 条里总拦截 **44 = 2.6%**，其中 `C4/C5/C1a/C1b` **4 条判据从未触发**。
于是 `①-a = 1 − 2.6% ≈ 97%`，**数学上恒接近 100%，没有区分力**。

这一条补的是**正向条件**：单子里必须存在一个「能在代码/文案里搜索到」的串。

### 三档定义（只用创建时信息）

| 档 | 判据 | 五线实测 |
|---|---|---|
| **L1 代码/文案级** | URL · IP · 错误码 · 型号/序列号 · **代码标识符**（camelCase/snake_case/`[x:y]`/全大写常量）· **引号里的系统提示语** · 文件名/路径 | **1.7%~17.6%** |
| **L2 组件/参数级** | UI 控件（按钮/弹窗/勾选框/页签…）· `X参数/X字段/X名称/X提示语/X文案` | 79.5%~97.5%（**无区分力**） |
| **L3 功能域级** | 只有数量+单位，或产品自定义业务对象词（`profile.anchorL3`） | 0~2% |
| **none** | 什么都没有 → `NOANCHOR` | 2.5%~20% |

### 三个必须防的假锚点（都踩过）

| 假锚点 | 来源 | 处理 |
|---|---|---|
| **流程/审批/扫描平台的链接** | `http://irdmspro…/workflow/need_change` · `http://defect…/approve/document` · `http://hikshield…/task/detail` · `https://zero…/pagespy` | `PROCESS_HOST` 黑名单排除 |
| **链接 query 参数被当成代码标识符** | `…?flowInstId=…` → 假锚点 `flowInstId`；`…?fileId=…` → `fileId`；`…?task_group_id=…` → `task_group_id` | **先把 URL 从正文里摘掉，再跑 `codeAnchors`** |
| **整段用例被当成提示语** | 引号里是「观察预览画面引导流程测试数据：…预期结果：1.」 | 限 4~26 字 + 关键词在前 14 字 + 排除模板词（`预期结果/操作步骤/测试数据…`） |

### 口径变更

```
旧 ①-a = 1 − 排除率          → 废止
新 ①-a = ①-a(L1)            → 这才是「可定位」
新 ①-b = ①-b(L1) = ①-a(L1) && expectQuality ∈ {explicit,inferred}
并列披露 ①-a(L2) / ①-b(L2) = 「提到了具体界面」的宽松档
```

**与下游的一致性验证**：`①-b(L1)` 1.3%~14.5% 与 `S8 事后验证真命中`（hc 9.5%）、`盲测一次猜中改法`（hc 10% / led 20%）**同量级**。
而旧的 `①-b`（33%~79%）测的其实是「单子写得全不全」。

## S7 期望唯一性（`expectQuality`，与 verdict **正交**）

`verdict` 只答「改哪里」，`expectQuality` 答「改成什么」。

| 档 | 判据 |
|---|---|
| `explicit` | 预期段有效（非空 + 非通用通过标准 + 非抄标题 + 与标题有**实词 2-gram 交集**）**或** 给了对照基准/具体值（`插件下有` / `与550基线不一致` / `与X一致` / `设计稿` / `CS端…可以`） |
| `inferred` | 标题自带方向词：`应…(显示\|为\|置灰\|禁用\|隐藏\|保留\|对齐\|重置\|改成\|提示)` / `需要…` / `要改成` / `应显示为` / `不显示` |
| `ambiguous` | 有对象有现象，但目标不唯一（`不一致` 无参照物、`没有` 无方向词） |
| `absent` | 连现象层都不够（`有2处异常展示`、`显示异常`） |

**严格可修**：

```ts
strictFixable = verdict === "FIXABLE" && expectQuality ∈ { explicit, inferred }
```

两个反直觉的实现细节（都是被实测打出来的）：

1. **不能用「预期段与标题 3-gram 重叠」判相关性**。led 的预期段写得最好，但用词与标题完全不同 → 3-gram 重叠普遍 <15% → 会被误判成 `ambiguous`。
2. **通用通过标准不算 explicit**。`界面正常加载 / 显示正确 / 无异常 / 符合预期` 去掉后几乎不剩实质内容的，等于没写。
3. **「与 X 不一致」算 explicit**（X 是参照物，目标=对齐 X），但「与**预期**不一致」不算（预期本身没给）。

## S9 类型分类（E 组 · `taxonomy.ts`）

**原则：按缺陷作用的代码层判，不按业务词。有序短路，顺序即优先级。**

```
1. hasCve          → 安全-SCA
2. hasScanner / [安全] → 安全-漏洞
3. profile.typeHints   → 产品线词表先行（同一句「显示不全」在不同产品线指向不同代码层）
4. 崩溃（排除否定式「没有崩溃」） → 崩溃与稳定性
5. 性能（较慢/超时/延迟/\d+秒后） → 性能
6. 环境（无插件…无法播放/启用控件/部署/灰度开关） → 环境与部署
7. UI_STRONG（溢出/截断/超出/乱码/边框/看不到/白色的点）且非无插件 → UI还原度
8. 兼容（火狐/safari/chrome/mac/机型/安卓1x）    ← profile.disableCompatType 可关
9. AX PRO 明细族（配置明细/结果明细 + 不符/未更新） → 逻辑
10. i18n（未翻译/英文/文案/key值）且非布局词 → 文案与配置
11. 资源（图标缺失/广告/旧图） → 文案与配置
12. AI（AI_SURFACE && AI_OUTPUT） → AI-Agent行为
13. 权限（权限/鉴权/未隐藏/被锁/仍可见/入口）   ← profile.disablePermType 可关
14. UI 词表 → UI还原度
15. 兜底 → 逻辑
```

**两个易错点（已固化为注释）**：
- `推荐` 不得进 `AI_OUTPUT`（已在 `AI_SURFACE`），否则 `AI_SURFACE && AI_OUTPUT` 恒真 → led 实测误判 3 条
- `小语种/俄语/阿语` 只是语种修饰，单独出现多为布局问题，不构成 i18n 类型

## S10 定位档（`locate.ts`）

**D1 判据（2026-10-29 扩）**：URL · 序列号 · 型号 · **代码标识符** · **引号里的系统提示语** · 引号提示语
**D2 判据**：UI 元素 · **设备/环境 IP**
**D3**：只有功能点

`codeAnchors()` 认 camelCase / snake_case / `[xxx:yyy]` / 全大写常量，**并排除伪锚点**
（`HiToolsDeliverySetupV2.2.0.1build260923_CN.exe` 这类安装包名长得像 camelCase）。

> ⚠️ **引号内容必须分两类**（hitools 踩过）：
> 引号里是**系统提示语**（含 报错/失败/不支持/找不到/超时/上限）→ D1（可 grep 文案）；
> 引号里是**用户输入指令**（`"配置设备OSD配置添加字符叠加…"`，hitools 358 条）→ **不是锚点**，
> 但可用 `extractReproInput()` 抽成复现指令。第一版不分导致 D1 从 35 飙到 394（62%）。

### 置信度上限（`confidenceCap`）

| 档 | 判据 | 含义 |
|---|---|---|
| **D1** | URL · 序列号 · 型号 · **代码标识符** · **引号系统提示语** | 可精确定位 |
| **D2** | UI 元素词（`tab/按钮/入口/侧边栏/导航/弹窗/卡片/图标/进度条/时间轴/下拉/横幅/标签`） | 组件级 |
| **D3** | 其余 | 只有功能点（最容易定位到错的代码） |

**置信度封顶**：

```
不可修 → low
D3     → 至多 medium
有附件缺口 → 至多 medium
D1 且无缺口 → 可达 high
```

**附件三档**：正文提附件/截图/录屏 → `evidence`；若 verdict 因附件依赖被拒 → `dependent`。

## 已知缺陷（必须随数字一起报）

| # | 缺陷 | 影响 |
|---|---|---|
| 1 | **default-allow**：86~98% 走 `default`，等于没判 | ①-a 语义只能是「没被已知模式拦下」 |
| 2 | **无仓感知**：纯文本函数，不知道「这个模块在不在本仓」 | D 档（安卓/设备侧）在 ① 全是 FIXABLE → ①→② 必然掉一批 |
| 3 | **VAGUE 覆盖极低**（hcp 5/159、led 1/319） | 含糊词表是误判补出来的；「实际段=标题复制」这个洞**未补**（hcp 93.7% 复读，规则一条没抓到） |
| 4 | **expectQuality 是粗筛** | hcp 校准：A 档召回 80%，B/C 误判 36% → 报数写「参考值 ±10pt」 |
| 5 | **配套 34.5% 明显低于人工 A 档 48.5%** | 它的标题极短（`雷达页面缺少停止标定接口`），规则把「缺少」判成 ambiguous，人工看是唯一的 |
| 6 | **不掌握「该给什么」也能判高** | 因为 `expectQuality` 只看「单子里有没有唯一解」，不看「这个唯一解对不对」。hcp #225/#226 我曾判 B，实际预期段给了邮件主题原文 → 应判 A（已修，A 99→104） |
| 7 | **许可式否定（「还可以/仍能」）被误判 absent** | 「亮色度校正执行任务时**还可以**调节校正工序生效」→ 期望其实是明确的（应该禁用），但无方向词 → 落 `absent`。led 全量只有 1 条（改判 inferred 后①-b **+0.3pt**），收益小但说明空洞：**「不应该允许」类句式缺一个词表**。同一轮 tier3 实测发现：`ambiguous` 的 5 条里 A 档 0 条，而 `expectQuality=absent` 的 4 条里有 1 条判 A → **与①-b ≈ ② 的假设一致，且反向验证了规则的保守性** |

### 与 ②/③ 的关系（别拿本文论证 ②）

```
①-a 95.0%   没被 8 类模式拦下
①-b 65.4%   单子给了唯一解        ← 本文到此为止
────────────────────────────────
②  A 档 65.4%   代码也给出唯一下手点 + 理解运行时可得性
③  78.0%        补设计稿/录屏/环境

```
