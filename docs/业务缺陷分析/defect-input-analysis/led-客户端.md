## 摘要

> ### ⚠️ 口径更正（2026-10-29）：①「可修率」应读作「可定位率」
>
> `verdict.ts` 的 `FIXABLE` 只表示「信息够定位」，代码里 `expectation-empty` 历史上**只进 evidenceGaps、不影响判定**。
> 已新增正交字段 `expectQuality`（explicit / inferred / ambiguous / absent），严格可修 = `FIXABLE && expectQuality ∈ {explicit, inferred}`。
>
> **「期望存在」≠「期望唯一」**：标题「A 没有 B」能推出期望（存在），但「两端不一致」推不出改哪端（不唯一）。
>
> | 口径 | 本产品线 |
> |---|---|
> | ①-a 可定位（原报告的「可修」） | 312 / 319 = 97.8% |
> | **①-b 严格可修（期望唯一）** | **220 / 319 = 69.0%（参考值）** |
>
> 期望不唯一的主因（按条数）：方向不唯一（两端以谁为准）· 目标值不唯一（距边界几 px）· 基准不唯一（以 550/CS 端为准）· 资源不唯一（设计稿）。
> 规则判定为粗筛（hcp 校准 80% 召回），权威值仍以人工/抽样的 A 档为准。

### 7.5 本轮最重要的方法论教训

> **基线择时不能取「缺陷批次开始前」，要取「缺陷引入之后、修复之前」。**

`#1102128` 就是反例：缺陷在 05-11~06-15 之间提出，而它的根因是 **05-11 之后的一次重构**（`resolveUniformSwitchState` → `resolveSendCardSwitchState` 时丢了取反）。
用 05-11 的基线去看，代码是**正确的**，只能判「需复现」；而真实修复 `e96d5de` 只改了一个 `!`。

**应对办法（已写入 `_pipeline.md`）**：
1. 能确定单条缺陷的提出日 → 用 `git rev-list -1 --before=<该日>` 取该缺陷专属基线
2. 只能取批次基线时，**必须再查一次「基线之后该文件是否被重构过」**（`git log --oneline <base>..HEAD -- <file>`）
3. 文件被改过 → 基线结论降级为「需复现」，不得直接标 A

### 8.4 两个条件各自买到了什么

**「描述完整 ＋ 带 UI」买到 ＋12pt —— 买的不是「能多做」，而是「不用猜」**

| 原来卡在哪 | 条数 | 补什么能解 |

**「AI 可接管测试环境」买到 ＋13pt —— 但有硬门槛**

三条同时满足才算「可接管」：

| 条件 | 现状 | 可行性 |
|---|---|---|
