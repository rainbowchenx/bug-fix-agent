# 跨产品线公共规则（hc + 配套-交通项目 实测）

> 来源：`规则提取/hc/rules.md` v2（200 条）+ `规则提取/配套-交通项目/rules.md` v1.1（200 条）。
> 只写**两条产品线都成立**的部分；差异留在各自的 `rules.md`。
> 分析流程（S0–S8、四档把握度、事后验证协议）见 [`docs/defect-input-analysis/_pipeline.md`](../docs/defect-input-analysis/_pipeline.md)。

## 1. 判定骨架（顺序即优先级）

```
去重 → 字段裁剪 → C7 生产者分流 → C3 归属非代码 → C2 期望未定义
     → C4 运行时依赖 → C5 附件依赖 → C1 不可断言 → 默认可修
     → E 组类型 → F 组定位档 + 证据缺口
```

短路顺序**不放宽**：越靠前的条件越硬。

## 2. 字段纪律

| 规则 | 依据 |
|---|---|
| 只用**创建时刻**就有的字段 | 用 `解决方法`/`验证结论` 等于用答案判题 |
| `缺陷处理说明` 里的 `<img>` **必须 forbidden** | 那是**修复后**截图，当成缺陷证据会得出「界面正常 → 缺陷不成立」的反向误判 |
| `所属模块` 两条产品线都不可用作分簇键 | hc：`Open` 单 3/16 有值；配套：83% 是「其他」 |
| **分簇键按产品线定** | hc = 标题 `[...]` 前缀；配套 = `测试模块` |
| 附件本体缺失时**不判死** | hc 33 条提附件、依赖型 **0**；配套 0 条提附件 |

## 3. 跨产品线成立的核心判定

| # | 规则 | 证据 |
|---|---|---|
| K1 | **「可修」= 信息够不够判，不是「技术上能修好」** | 配套 5 条「参数下发失败」分不清前端/设备端，仍判可修 |
| K2 | **「描述不可断言」必须基于「实际结果段」，不能用预期结果段** | hc 26 条预期结果是模板话术，扫全文会误杀 3 条可修缺陷 |
| K3 | **「空模板 ≠ 不可断言」（D6）** | 配套 22 条实际结果为空，21 条标题自足；hc 9 条同类 |
| K4 | **「提附件」不构成放弃理由（D2）** | 两批合计 33 条提附件、依赖型 0 |
| K5 | **不用 `严重级别` 排优先级（D3）** | hc `低` 123 条中 113 可修；配套 `高` 3 条全是 CVE |
| K6 | **不用描述长度做阈值（D1）** | 17–20 字的标题可修；982 字的也可修 |
| K7 | **扫描器生产者必须单列 `SCA`** | hc 0 条；配套 11 条（含无 CVE 号的 HIK-VUL） |

## 4. 跨产品线成立的反模式（不当判据）

| 反模式 | 为什么错 |
|---|---|
| 「提到 X 就放弃」 | `附件`/`基线`/`需确认` 都出现过「提了但仍可判」 |
| 「形容词词表一刀切」 | `显示不全` 在 hc 是话术、在配套是真现象 → **词表必须按产品线调** |
| 「类型按业务词判」 | 同一句「未翻译」在 hc 是 i18n、在配套 403 机型上是布局 |
| 「端归属靠文本猜」 | 需要仓库边界；`无插件` 在 hc = 产品设计、在配套 = 测试矩阵 |
