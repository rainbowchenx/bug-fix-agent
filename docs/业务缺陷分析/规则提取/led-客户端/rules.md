## 2. 分簇（B 组）

### B1 标题前缀**不可用**

4 种前缀，`LED Tool-校正工具` 占 **309/319** → 分簇等于不分。

### B2 改用 `所属模块`（多值逗号标签）

规则：拆分 → 去空/None → **优先取含 `/` 的层级项，否则取最后一项**。

```
结构,校正工具,接收卡              → 接收卡
校正工具,校正工具,APP应用/交互设计   → APP应用/交互设计
```

结果 8 簇，覆盖 **319/319**：接收卡 123 · APP应用/业务逻辑模块 78 · Android系统/参数初始化 37 · (未标注) 25 · APP应用/交互设计 25 · Windows应用/交互设计 18 · LED显示屏APP/主要功能 11 · 串口SDK/参数配置 2

> 实现：`src/defects/tag.ts` `clusterKeyOfModule()` + `profile.clusterFrom = "moduleTag"`。
> `所属模块` 在 hc/配套 明确**不可用**（hc Open 单 3/16；配套 84% 是「其他」）→ 分簇键必须逐产品线实测。

### B3 不切业务组

显示产品测试组 246 + 控制产品测试组 72 测的是**同一个产品**（LED Tool 校正工具），前缀几乎全一致 → 不切。
（对照：hc 里 HPP 那 14 条是另一个产品，必须切。）

## 3. 判定（C 组）

顺序与 hc/配套 一致，**只追加不重排**：

```
C7 生产者分流 → C3 归属非代码 → C3b 设备侧 → C2 期望未定义
  → C4 运行时依赖 → C5 附件依赖 → C1 不可断言 → 默认「可修」
```

### C7 生产者分流

319 条**无一条**来自扫描器/漏洞扫描（质量特性里无安全类）→ 不做 SCA 分流。

### C3 归属非代码

| 规则 | 状态 |
|---|---|
| `dirty-env` `plugin` `browser` `product-decided` `resource-swap` `impl-suggestion` | 保留 |
| **`service-down`** | **禁用** —— LED 的「校正服务」是随客户端启动的**本地服务**，插拔相机/亮度计时的服务异常属客户端异常处理缺陷 |
| 新增：驱动/环境 | `/重装驱动\|驱动后正常\|驱动异常\|驱动问题/` → NOTCODE |

依据：`#0203279` `#1206817` `#1103562` 三条「校正服务异常」在禁用前被误判 NOTCODE。

### C3b 设备侧

未启用。本域「接收卡/发送卡掉线」看似设备侧，实为**客户端异常提示缺失**（如 `#1104842`「接收卡掉线无任何提示，进程正常进行下去」）→ 前端可修。

### C2 期望未定义

| 规则 | 依据 |
|---|---|
| 标题/正文含 `【需求】` | `#1203485` `#1205656` |
| `需求…定义/要求…不一致` 或 `无法验证…参数/性能` | `#1402247` |
| **保留** `保持一致` → DESIGN | `#1202298`「两数最小单位应保持一致」**未定以哪边为准** |

### C1 不可断言（本域 2 条）

| 规则 | 依据 |
|---|---|
| VAGUE 词表**只加**「显示异常」 | `#1805190` 实际结果段=标题，没说怎么异常 |
| **不把「异常」入表** | 52 条含「异常」，绝大多数带具体位置 |
| **抑制**「显示不全」「偏移」 | 「显示不全」是本域**真实现象**（拓扑预览超出）；「偏移」是提示语名称（「镜头有偏移的提示信息未翻译」） |

## 4. 七条全局修正（F1–F7）

> 这七条不只影响 LED，写在 `src/defects/verdict.ts` / `taxonomy.ts` 里。
> 修完复跑 hc 与配套：**两条基线均未回退（verdict/reason 各 200/200）**。

| 编号 | 位置 | 修正前 | 修正后 | 误判实例 |
|---|---|---|---|---|
| **F1** | C5 附件 | 裸 `上传失败` → 判 ATTACH | 必须与 `附件/截图/录屏` 同现 | `#1201223` 热力系数上传失败、`#1200874` 系数上传任务失败（业务现象） |
| **F2** | C1c/C1d | 缺提示类被含糊/性能判死 | `增加/缺少/没有…提示` 豁免 | `#1400451` 需增加等待提示 |
| **F3** | C1e | 「不报错」被判「报错无位置」 | `不/未/没有 + 报错/拦截` 豁免 → 缺校验 | `#1206625` 滑到异常值不报错 |
| **F4** | C1c | i18n 现象被含糊词兜底 | `未翻译/翻译显示/词条` 命中则跳过 VAGUE | `#1403295` `#1403048` |
| **F5** | `AI_OUTPUT` | 含「推荐」，与 `AI_SURFACE` 重复 → 恒真 | 移除「推荐」 | 3 条含「其他值选择工具推荐值」被判 AI 行为 |
| **F6** | `CRASH` | 不看否定 | `(没有\|未\|无\|不)崩溃/闪退/白屏` 不算 | `#2902156`「子系统没有崩溃」 |
| **F7** | C1e | 标题含「失败」+描述短 → 判「只写报错」 | 因果结构（`导致/致使/造成/引起`）豁免 | `#1201223`「系数上传失败**导致**流程未自动执行」 |

**F5 是值得记录的基础 bug**：`AI_SURFACE && AI_OUTPUT` 双条件本意是「有 AI 场景 + 有 AI 输出异常」，但「推荐」同时出现在两边，导致任何含「推荐值」的缺陷都被判成 AI 行为。

## 8. 无法规则化（已知边界）

| 议题 | 说明 | 影响 |
|---|---|---|
| **bug vs 需求变更** | `缺陷类型` 全空；只能靠标题 `【需求】`（2 条） | 至少 `#1202298` 这类「易用性优化」介于两者之间 |

| **描述与标题不匹配** | `#0201126`「分区的迭代校正文件放的位置不对」，实际结果段却是另一条缺陷的现象 | 单条级，无法规则化 |
| **类型一致率无全量基线** | 只有 45 条人工核对 | 见 §9 |

## 9. 基线强度（必须与 hc/配套区别对待）

| 产品线 | 人工基线 | 泛化验证 | 读数可信度 |
|---|---|---|---|
| hc | 200 条全量 | ✅ 50 定型 → 150 首跑 = **89.3%** | 高 |
| 配套-交通项目 | 200 条全量 | ⚠️ 部分 | 中 |
| **led-客户端** | **45 条**（7 不可修全量 + 40 分层抽样） | ❌ **无** | **低** |

- 人工子集 verdict **45/45**、类型 **45/45**
- 全量 319/319 是**回归快照**（规则输出），**不是准确率**

**下一步必须做**：新一批 LED 导出进来时，**先跑本规则、不改规则**，直接统计首次未见数据的一致率。那才是真正的泛化读数（hc 的基准是 89.3%）。
