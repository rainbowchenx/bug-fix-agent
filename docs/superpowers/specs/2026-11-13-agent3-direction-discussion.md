- 每条缺陷都需要分析报告：无法修复、描述不足、目标不在当前工作目录的仓库等情况，必须说明该票的分析、原因与缺失信息。

## 2. 当前实现事实（供讨论，不等同目标设计）

- 当前 Agent-3 是逐票只读 analyze SDK → 可选独立 fix SDK → 收集 patch → 完整报告。
- skill 已支持 analyze/fix/bugfix 等 profile 和 overlay 优先，但 fix 禁止 Bash，提示词禁止执行测试；因此当前注入 skill 无法独立弥补验证工具能力缺失。
- 报告和 HTTP 运行状态已落盘，但尚未看到正式的按缺陷反馈、版本化补充、再次执行协议。
- analyze 中的 session_id 主要用于预算耗尽后的短暂恢复；尚未建立持久的缺陷级会话/证据/工作区恢复体系。
- 当前还存在占位根因可以通过改码门禁、worktree 复用/基线、多仓修改、新增文件补丁完整性等问题，详见调研报告；这些需要与方向讨论分开，不以局部bug替代架构讨论。

## 3. 助手提出的建议（尚未由用户逐项确认）

### 3.1 业务 skill 与通用执行底座

- 赞同以业务 skill 承载业务规则、模块映射、修复方法、验证策略，而非平台硬编码每个项目的测试流程。
- 通用 Agent-3 提供工具调度、工作区、运行记录、有限反馈循环和报告；业务 skill 决定具体怎么操作；实际执行证据决定可以声称什么。
- 技能指令不等于执行能力或成功证据；需要相应工具支持，并记录未能执行的前提。
- 保留无完整环境下产出未验证补丁的能力；能执行时使用反馈，不能执行时给出准确的剩余验证范围。

### 3.2 报告作为后续协作入口

- 报告按票记录：当前理解、已读证据、已尝试操作、当前结论、阻断原因、具体需要补充什么和为什么需要。
- 区分“未定位到代码”与“证据指向当前工作区之外的代码”；不能因为搜索无结果就断言不在本仓。
- 区分缺陷未解决、补丁已生成但未验证、修复被用户否定、验证依赖实机等状态。
- 每轮自动执行并结束，用户在轮次之间补充后触发新尝试，不必保持一个运行进程无限等待。

### 3.3 同一缺陷、多次尝试

- 一个缺陷保留持续记录，每次执行为独立 attempt，保存输入版本、报告、补丁与反馈的父子关系。
- 用户以补充/反馈提交新信息，不直接改写旧模型结论；历史保留，当前事实形成新版本。
- 记录旧补丁是未应用、已应用、已人工修改还是已丢弃；下一轮不能无条件叠加旧补丁。
- 新反馈可以推翻旧假设，失效结论不得继续作为已确认事实。
- 补足信息后重新判断原阻断；不能永久被首次 needs_info 分类跳过。
- 重跑范围按变化决定：补日志通常无需重跑 Agent-1/2，换代码仓/版本需要刷新相关知识。此为建议，尚未定具体职责。

### 3.4 上下文保存与共享

- 建议完整保存可获得的执行记录，用于审计、检索和回放；不承诺可保存模型内部不可见状态。
- 建议按缺陷维护持久化状态：事实、用户陈述、待验证/已否定假设、代码基线、当前补丁、验证和阻断。
- 当前推理上下文按需组装，不每轮重放所有历史；关键原文和证据保留引用，摘要不是唯一存档。
- 同一缺陷的 analyze/fix/后续尝试共享受管理的状态与证据；不同缺陷不共享全部临时推理。跨票共享可核实项目知识。
- 会话恢复可作为优化；同基线短期延续可 resume，换方向可分支，换仓/版本或历史污染严重时新会话加载有效状态。
- SDK 会话只保存对话，不保存代码工作区；会话恢复必须配套确认代码版本、实际文件和旧补丁状态。

### 2026-11-13：Git历史产物审阅

已读取11-12三仓77票的batch/knowledge，以及11-10 transport对照，详见[上游历史产物审阅](../../research/2026-11-13-agent1-agent2-historical-artifact-review.md)。没有把已移出版本库的整份工单JSON重新入库。

主要事实：仓级知识与部分符号调用链有价值；77票全部medium但质量差异明显；LED24/40票同组三个通用控制器；多个strict/explicit样本的步骤和期望与现象错位。原始导出和业务仓不可得，不能断言错位起因或真实修复成功率。11-13的Trellis和仓根修复晚于本批，不能把历史缺口一律当当前未修复。

助手进一步提出、尚待用户确认的方向：

- Agent-1更偏向保真资料准备与质量/冲突标注，不在读码前终局裁决可修性。
- 缺信息与禁止调查分开；允许Agent-3利用现有线索有限补证据，而不是永久跳过needs_info。
- Agent-2稳定仓知识与票级动态检索分开，避免候选填充和与Agent-3重复调查。
- 工具来源、调查状态、证据强度分别表达；run完成或全有候选不等于定位有效。
- 原始材料、补充与每次尝试在缺陷级持续记录中关联；已明确无需保持旧契约兼容。

### 2026-11-13：Agent-2分工讨论更新

用户补充实际使用反馈：把Agent-1和Agent-2产物交给对应业务项目目录下的Claude Code后，后者认为Agent-2逐票分析对后续修复很有帮助，可复用仓库知识帮助较小；这也是用户此前加强Agent-2分析的原因。

助手据此调整此前倾向：目前不建议将Agent-2收缩为仅维护仓库知识，应保留逐票前置调查。此为助手建议，尚未冻结分工或方案。

- 仓级知识解决系统组织问题；逐票调查解决中文业务现象到具体代码链路的连接。已在项目目录工作的Claude Code可能更需要后者。
- 三批产物中，配套的具体函数/协议/提交聚合关系、LED的计算属性/i18n键体现了逐票分析价值；重复控制器与文件名碰撞体现的是质量不足，不足以证明应删除逐票调查。
- 允许Agent-2记录已经发现的根因假设，不因角色划分刻意停止有价值调查。Agent-3仍核实关键因果关系并对最终修复负责。
- 重读编辑目标的当前代码是必要核实；重复猜业务入口、重走已排除路径、重找已定位错误码才是应减少的浪费。
- 前置调查应可恢复：事实、假设、已排除项与剩余问题分开。用户补日志可沿原链核实；否定修复可使假设失效；换仓/版本需要重新判断适用性。
- 二次投递不机械地重跑Agent-2；Agent-3能继续时直接继续，涉及新入口/新仓或显著版本变化时再补调查。
- Claude Code认为有帮助是重要使用证据，目前支持减少调查难度；最终修复正确率还需实际验收结果佐证。不会要求用户先做完整实验才继续讨论。

### 2026-11-13：用户后续可补充材料清单

用户表示材料后续补充，本轮不等待这些材料，不要求提供完整业务仓。

建议先选三类案例：Agent-2明显帮上忙的一票、线索帮助小或有误的一票、需要补信息后再修的一票。优先取得一张成功修复票的完整链路。

每票按方便程度提供：

1. 原始工单：标题、描述、步骤、测试数据、前置条件及附件说明；对应Agent-1条目，用于检查信息丢失和字段冲突。
2. 对应Agent-2产物：候选、理由、符号/调用关系；如有则提供工具过程、注入业务skill及版本。
3. Claude Code接手过程：完整导出或关键片段，重点是用了哪些上游线索、推翻哪些判断、重新调查什么，以及认为有帮助的具体理由。
4. 最终修改和结果：脱敏diff、关键函数或修改说明；是否修好、如何确认、人工补改。未验证也可提供，不要求补造验证。
5. 二次修复案例：首次结果、用户不满意之处、补充信息、第二次调整和结果。

可用相关函数与必要调用处代替完整代码；无法给代码时可用模块关系与关键行为说明，但不能据此独立确认源码机制。材料可按用户方便逐步提供，无需一次齐备或专门重跑整批。

### 2026-11-13：内置开源skill与按需触发（讨论中）

用户提出：Agent-3可能未充分注入优秀开源skill；希望考虑内置经过选择的开源skill，并根据项目实际情况触发。用户尚未要求安装或实现，本轮只调查与讨论。

本轮代码核查事实：

- Agent-3已有内置hierarchical-localization、systematic-debugging、test-triage、typescript-null-safety、vue-debug、electron-process-boundary、monorepo-workspace等短版SOP；不能说完全没有技能支持。
- 包内技能通常向system prompt提供名称、描述和路径，要求命中时读取；overlay内联正文最长2400字符。available/bound不证明实际完整读取或应用。
- 自定义frontmatter解析在description为YAML多行块时返回空字符串；导入使用此写法的技能可能丢失触发描述。当前还按agent profiles过滤，第三方skill的元数据未必与此一致。
- 未见把完整上游skill包、支持文档/脚本及版本来源作为一个统一受管资源接入的证据；不能仅凭同名技能认定已引入完整开源实现。
- 现有SDK调用主要自定义prompt附录，未在所读调用中显式配置包内plugin路径。项目本地skill是否被SDK原生发现，还取决于实际SDK/CLI版本和会话设置，需运行日志核实，不能静态断言全部未加载。
- fix禁止Bash且提示词禁止测试，依赖脚本或浏览器的技能即使被读取也可能无法执行。

助手建议，尚未确定为方案：

- 支持精选开源技能库，但先保证发现、适用性选择、完整读取、工具执行与证据记录这条链路；不以技能数量作为效果指标。
- 业务skill承载产品事实与实际验证方法；开源skill提供通用诊断、框架排查、浏览器操作等方法。通用要求不能覆盖项目实情，且技能均不能改变执行边界和事实记录。
- 按缺陷意图、实际代码框架、当前阶段及可用环境选择技能，允许中途发现新信息后再触发；不是给整个项目固定贴一个标签，也不是每票注入所有正文。
- 保留上游来源、版本及必要支持资源，适配后标明差异；不通过截断把关键步骤和引用变成不完整说明。真正纳入发行包前核对许可。
- 通用debugging/TDD/完成验证等技能需核对适用性，避免强制所有票具备本地复现、完整测试或中途人工确认，破坏已讨论的异构环境与轮次间反馈模式。
- 每票记录技能版本、触发依据、实际读取/应用步骤与结果。第二轮复用的是操作结果与未完成步骤；新增反馈可触发新技能，不因上轮加载过就默认本轮仍适用。

本轮核查的候选来源：

- [obra/superpowers systematic-debugging](https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md)：根因调查、跨组件取证、数据流追踪、对照正常路径与假设检验；完整技能还引用额外技术文档。
- [obra/superpowers verification-before-completion](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md)：按证据限定完成声明。适配需区分已生成patch与行为已验证，不能转成无环境就不交付。
- [anthropics/skills webapp-testing](https://github.com/anthropics/skills/blob/main/skills/webapp-testing/SKILL.md)：Playwright、服务生命周期辅助脚本、DOM/截图与日志操作；需相应工具与可用页面，不保证适用设备持续连接、实机依赖等场景。
- [SDK技能发现与调用说明](https://code.claude.com/docs/en/agent-sdk/skills)：原生发现与按需加载机制可作实现选项；具体API须核对项目实际安装版本，本轮不冻结接入方式。

### 2026-11-13：每票上下文与二次修复的进一步讨论要点

- 建议一票持久保存四类内容：最新有效事实/未决问题、每轮操作与证据历史、代码及补丁状态、实际用过的技能与版本。原始会话可保存用于追溯，但不是唯一事实来源。
- 用户补充后先理解其改变了什么：补事实、补验证结果、否定假设、修改预期、提供新仓或代码版本；再决定从何处继续，而非默认重新分析整张票或继续旧修复。
- 有效事实、暂定假设、用户陈述与工具观测应有来源和状态；保留被否定结论作为历史，避免再次踩坑，但不继续当当前前提。
- 会话恢复用于连续工作；新会话同样应能从缺陷记录和实际workspace恢复。用户反馈跨天、换机器或旧会话不可得时，不应丢失业务进度。
- 新一轮重新选择适用skill：例如首次定位时只用调用链调查，补充俄语截图后再采用国际化排查；没有浏览器/设备时只记录待执行步骤。
- 本轮仍讨论记录颗粒度、恢复语义与技能协作，不编写字段schema、API、存储方案或实施计划。

### 2026-11-14：完整例子与SDK会话职责边界

已将“Electron校正时相机断开，首次缺消息/期望→用户补充→二次修复”的完整虚构示例保存为[每票上下文与用户反馈示例](2026-11-14-agent3-feedback-context-example.md)，含假设更新、技能选择、会话续接与新开、候选A/B和用户已应用旧补丁等分支。它不是实仓成绩或正式方案。

用户要求继续讨论SDK自身能力与业务持久化的分工，暂不写方案。助手当前建议：

- SDK负责会话历史及恢复/分支，避免自行重复建设通用对话存储；应用负责缺陷身份、attempt与多会话对应、当前有效事实、用户反馈版本和报告/补丁状态。
- 会话ID只是查找标识；还需保证对应会话存储可得，跨主机时保存/迁移或使用适用的外部存储能力。具体接口取决于实际SDK/CLI版本。
- 会话恢复不恢复代码；文件checkpoint也不是完整仓库与环境快照。对话分支不自动创建worktree，回退文件不会撤销旧对话中的结论。
- 关键证据有来源、版本和适用场景，区分用户陈述/工具观测/模型推断。附件、截图、patch不能只靠会话中一个临时路径存在。
- 二次投递先对应旧反馈轮次与实际代码/补丁，再选择续接、分支或新会话；新增事实和失效假设显式交给模型。
- 保留完整会话便于追溯，同时维护可恢复的有效缺陷记录；SDK会话不可得时仍可新开继续。当前代码只用局部session_id做预算抢救，未把分析/编辑会话映射持久写入报告。
- 作为每票持续协作基础的关键状态持久化，不能沿用当前尽力保存artifact且吞写盘错误的语义宣称“可恢复”；这一点是可靠性边界，具体处理方式待方案阶段决定。

本轮只记录语义与边界，没有确定数据schema、数据库、SDK具体API或实施计划。
