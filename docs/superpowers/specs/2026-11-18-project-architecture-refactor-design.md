# 项目架构优化方案

- 日期：2026-11-18
- 代码基线：`main`，`cfcb8a1`
- 状态：设计评审稿
- 依据：[三 Agent 架构](2026-11-03-three-agent-architecture.md)、[Agent3 修复与反馈设计](2026-11-15-agent3-repair-feedback-design.md)、[Agent2 调查保全与 Agent3 反馈收敛设计](2026-11-17-agent2-lossless-handoff-agent3-convergence-design.md)及其[实施计划](../plans/2026-11-17-agent2-lossless-handoff-agent3-convergence-plan.md)

## 1. 现状和目标

| 现状 | 维护成本 | 本次调整 |
| --- | --- | --- |
| Agent1 和 Platform 已有独立入口及打包边界，共同使用 `contracts` | 这部分职责已经可辨识 | 保留两种交付和共享契约，Agent1 只参与相关测试和打包验收 |
| 首跑经 `workflow/run.py` 和 LangGraph，续跑由 `cli.py` 实现状态加载、锁和报告合并 | 两条正式入口对写回和恢复的处理分散 | 把续跑和反馈导入移入 `workflow`，让首跑和续跑复用报告持久化规则 |
| Agent2 的分组恢复在 `cartographer`，字段容错和合并也出现在 `sdk/cartography.py` | 一组模型输出在何处被保留、降级或视为完成，需要跨层追查 | 由 Agent2 统一解释调查结果和交接状态，SDK 交回原始输出及执行信息 |
| Agent3 的 `analyst/run.py` 同时负责批次、逐票决策、候选修复和报告组装 | 读单票的执行路径需要先理解整批调度 | 明确批次入口、一次逐票尝试、产物提交三个边界 |
| `pytest` 只收集 `tests/`，部分夹具在 `test/fixtures/`，评测脚本位于 `packaging/` | 测试、评测和发布入口难以辨别，样本路径散落 | 合并共享测试夹具，划出 `evals/`，把归档批次与可执行用例区分开 |

本次优化以正式链路更易理解、改动更易验证为目标。修复效果继续以真实项目和用户验收评定。报告默认只读，编辑须显式授权。逐票调查、用户补充、候选验证、会话降级、补丁基线判断沿用既有设计。R10 维持原议题状态。Agent2 现有预算配置和最多两轮 JSON 收尾的触发条件纳入回归，预算结束与格式错误分别保留诊断。

## 2. 目标结构

```text
agent1/                         缺陷导入、整理、独立交付
platform/bugfix_platform/
  cli.py、http/                 参数、请求响应、退出码和运行状态展示
  workflow/                     批次编排、反馈导入、续跑、批次产物发布
  agents/cartographer/          Agent2 仓库分析、逐票调查、交接与恢复
  agents/analyst/               Agent3 批次调度、逐票尝试、修复和验证
  sdk/                          Claude SDK 调用、会话、执行信息及响应读取
contracts/                      跨 Agent 与对外交付的契约
tests/
  agent1/、platform/、contracts/  既有工程测试分组
  integration/                  正式入口的跨模块测试
  fixtures/                     缺陷样本、微型仓库、质量回归夹具
evals/                          离线评分脚本、专用评分用例
packaging/                      构建、发布和部署配置
docs/                           当前开发入口、设计决策和评测记录
```

这是职责图。实际文件以现有模块为起点，只有职责明确变化时才移动或新建。运行日志、用户反馈和补丁继续保存在运行产物目录。根目录的 LangGraph 配置供源码运行，发布包配置由构建组装并校验导出的图入口。

### 调用和状态归属

1. **正式入口到用例。** 首跑复用现有 `run_three_agent_workflow`。CLI 和 HTTP 运行器调用这一入口，LangGraph 部署入口复用同一批次节点。反馈导入与单票续跑各有一个用例入口，续跑按当前语义支持预览、执行分析和显式授权修复。CLI 保留参数、输出和错误映射。HTTP 的 run metadata 继续负责展示运行状态，续跑 HTTP API 留待实际需求驱动。
2. **Agent2 到 SDK。** `cartographer/run.py` 组织阶段，`investigation.py` 和现有 store 持有分组身份、状态和恢复规则。SDK 识别会话与终止类型、提取结构化响应，保留原始输出。Agent2 按票解释字段、标记丢弃或降级原因、合并有效调查并生成 `CodeKnowledge`。合法空候选、未调查、部分调查、完整调查可区分。接收异常字段后仍有效的结果可以继续交接，来源和证据状态随结果保留。
3. **Agent3 到逐票尝试。** 批次入口选择目标票、遍历和隔离单票异常。首跑与续跑调用同一逐票流程，从已知证据及反馈推进到本轮结论。已有证据、提问、候选修复和检查规则留在各自实现中。以逐票流程串起这些规则，避免按行数拆出大量只转发参数的小文件。
4. **写回与恢复。** 运行产物目录的排他锁保护续跑的父轮选择、尝试提交和报告发布。按既有提交顺序保存 attempt 和分析快照，确认齐备后推进 latest。报告生成复用同一套逐票合并、汇总重算和渲染逻辑，保留其他票、轮次文件和日志引用。恢复优先读取已提交状态，通过现有报告恢复路径保留历史票和元数据。LangGraph checkpoint 负责批次编排，Claude SDK session 负责对话续接，逐票记录负责业务恢复。
5. **共享契约。** Agent1 和 Platform 通过 `DefectBatch` 交接。Agent2 到 Agent3 通过 `CodeKnowledge` 传递证据，`AnalysisReport` 发布结果。契约层只容纳跨边界的模型与校验。Agent 专属的中间步骤或状态留在所属模块。

## 3. 架构脚手架

以现有代码中的 `resume` 用例作为参考实现。默认采用直接函数调用、已有类型和 pytest。新能力有一个清楚的放置规则，开发者可以从根 README 进入架构说明并找到对应入口及测试。

| 规则 | 可执行检查 |
| --- | --- |
| Agent1 和 Platform 各自可导入，共享契约不依赖两者 | 延用包边界测试，覆盖契约的反向依赖 |
| Platform 的 CLI/HTTP 把 Agent 执行委派给 workflow，SDK 不依赖 Agent、workflow 或传输入口 | 扩展现有边界测试，约束源码导入和入口委派，错误输出指向导入位置。SDK 类型或通用配置可共享，业务规则由 Agent 解释 |
| Agent2、Agent3 通过产物交接 | 用已有集成测试经正式首跑入口验证产物校验和失败分类 |
| 正式入口的续跑行为可复现 | 增补覆盖缺口，集中走 CLI `feedback`、`resume` 与首跑入口，保留 SDK 调用边缘的替身 |
| 构建出来的包可独立使用 | 用当前构建脚本检查两种交付，并从源码树之外验证打包入口及所需资源 |

脚手架维护面限于架构说明、参考实现和可执行检查。暂不增加生成器、通用 Agent 基类、插件注册系统或新的工作流引擎。等有多个同类入口需要反复创建时，再基于已验证的结构评估生成模板。

## 4. 迁移顺序与验收

| 优先级 | 改动范围与依赖 | 验收标准 |
| --- | --- | --- |
| P0 · 基线 | 记录当前 CLI、HTTP、LangGraph、打包及评分入口，标出已有工程回归。定位所有夹具与评测引用 | 记录全量测试收集清单和跳过原因。现有正式入口的参数、退出码、产物类型以及同一批评测的输出有可重跑的基线 |
| P0 · 续跑样板 | 基线后抽出反馈导入、续跑用例与复用的报告持久化逻辑。沿用现有 attempt、快照和锁 | 正式 CLI 能首跑出报告、导入用户反馈、预览或执行。上一轮上下文进入新尝试，重复提交和并发保持既有语义，损坏汇总可以恢复，其他票保留。HTTP 和独立 LangGraph 首跑交付路径通过回归 |
| P1 · Agent2 交接 | 基线后调整 `sdk/cartography.py`、`cartographer/run.py` 与分组调查模块之间的职责 | 混合好坏条目仍保留 SDK 合法证据和来源。部分组不视为完成，零预算下仍恢复所有已完成组。相同输入下预算停止和 JSON 收尾行为符合基线 |
| P1 · Agent3 单票流程 | 续跑样板后从批次循环中提取逐票流程，集中复用分析、编辑门槛和检查结果汇总 | 首跑和续跑使用同一逐票入口。报告模式不编辑，反馈后具备证据与授权的用例可以进入修复。补丁状态、候选验证、回修和历史日志一致，单票异常保留其他票 |
| P1 · 目录归位 | 基线后可以独立进行，单独提交路径迁移。共享夹具并入 `tests/fixtures/`，评测脚本移至 `evals/` 并更新活跃引用 | `pytest --collect-only` 前后用例集合一致，另行核对新增检查。夹具可从测试和公开示例访问。固定报告和人工真值的评分结果一致。两类构建可用 |
| P2 · 文档及产物归档 | 明确实际归档位置与访问方式后整理。保留历史方案中的原始证据引用，给活跃开发者文档标出当前入口 | 根 README 能到达测试、评测、构建和架构说明。历史设计和证据可以定位。已有受版本控制的 ZIP 在复制和校验可读前留在原位置 |

目录迁移与业务抽取各自提交。已发布的 CLI 和 HTTP 行为、契约格式、运行产物的读取路径按本次基线验收。内部 Python 导入和评测脚本路径可以随迁移统一更新。若抽取时碰到需要改变业务结论的问题，另列修复和验收，避免重构与效果变化混在同一次验证里。

## 5. 交付判定

- **工程验收**运行全量 `pytest`、全量收集核对、两类交付构建和正式入口烟测。构建可先通过 `python packaging/build.py all --skip-exe` 检查组装，Agent1 发布环境另验完整可执行产物。复跑同一组评测用例，对比评分及关键业务字段。时间戳、会话 ID 和临时绝对路径按既有语义比较。
- **重点用例**复用 [Agent2 分组恢复](../../../tests/platform/test_investigation_progress.py)、[Agent3 续跑入口](../../../tests/platform/test_repair_cli.py)、[跨 Agent 集成](../../../tests/integration/test_handoff_feedback_convergence.py)和 [HTTP 运行入口](../../../tests/platform/test_http_runs_api.py)。覆盖不到的正式入口环节再补测试。
- **实仓复验**用相同模型、同一仓库基线和同一批缺陷做配对。分别看 Agent2 有效调查的交接情况和 Agent3 收到有效补充后的收敛。用户实际应用、回归验收之后记录修复成功率。结构调整的工程通过与真实项目的修复验收分别记录。
- **可读性验收**走读三条主线。调查结果如何进入 `CodeKnowledge`，一张票收到反馈后在哪决定是否编辑，报告损坏后用什么恢复。每条主线应在所属入口读到步骤，并能定位负责该决策或持久化的模块。
