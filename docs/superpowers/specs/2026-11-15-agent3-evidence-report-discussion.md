# Agent-3 证据门槛、调查边界与报告讨论补充

日期：2026-11-15。性质：对近期对话的追记，区分用户约束与助手建议。主记录：[方向讨论](2026-11-13-agent3-direction-discussion.md)。

## 用户补充并明确的约束

- 二次投递可采用 Git HEAD 关联每轮代码状态的思路；实际工作区还需核实，不能据此认定 Agent-1 当前已提供完整快照。
- 业务环境复杂：有单测则确保相关单测正常，适用的语法检查和编译正常；业务 skill 或补充信息提供测试环境方法时，按说明启动并验证。
- 票面可能模糊、缺图/环境或不属于当前仓库，如设备硬件、C++ 算法、浏览器插件、固件或原生 App；必须判断，允许请求用户二次补充截图、UI 参照和必要环境。
- 后续提供三个项目类型的原始票与 Agent-1/2 产物，辅助判断上游质量。Agent-2 应优先减少幻觉和完全错误的信息。
- Agent-3 产出覆盖所有缺陷的完整报告。用户自行选择合理改动、应用并验收，然后反馈；不自动推送代码仓或部署生产。
- 用户已授权从讨论进入完整方案产出，要求标注日期、关联讨论 Markdown；本轮未授权实施产品代码。

## 助手建议及其理由

- 改码需要明确预期、代码归属、受证据支持的失败机制和修改论证；关键不确定性不再改变修法时可编辑，不要求所有票先实机复现。
- 诊断性修改与修复候选分开，不能把加日志当修好。
- HEAD + dirty 文件/未跟踪源文件状态 + 补丁身份共同识别实际代码；用户测试的构建还需要关联，不能由 HEAD 推定。
- 调查以能否消除关键歧义判断进展；无可获得区分证据、依赖外部组件或预算耗尽时收尾。归属未知、疑似外部与已证实外部分开。
- 请求材料应解释为什么需要、会影响哪个判断，优先少量高价值材料。
- 验证区分工程检查、用例/模拟覆盖与业务实测；原有失败、环境阻断和补丁引入失败分别处理。
- 报告采用批次概览 + 全量逐票详情；处理结果、验证情况与用户应用/验收状态分开。
- 补丁支持逐票选择，标明多票重叠、共享修复、依赖与未验证的组合效果。
- 反馈关联实际应用版本，允许未应用、部分应用、人工调整和未知；每轮报告保持历史，另汇总最新进展。
