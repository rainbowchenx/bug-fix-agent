# Agent-3 每票上下文与用户反馈：完整讨论示例

记录日期：2026-11-14。状态：讨论示例，不是正式方案。以下缺陷、日志与处理结果均为虚构，用于解释行为边界，不代表实仓验证成绩，不冻结字段、接口、存储或SDK用法。

主记录：[Agent-3方向讨论](2026-11-13-agent3-direction-discussion.md)。

## 1. 缺陷与项目背景

初始工单只有：

> 校正过程中相机断开，界面一直显示“校正中”，无法再次开始。

目标为Electron设备工具。工作目录包含桌面端，驱动服务在另一个仓库；业务skill说明任务状态通过IPC进入桌面端。Agent-2已给出校正页面、状态管理与IPC入口的逐票调查线索。

```text
第一次分析 → 缺少失败状态证据 → 报告需补信息，结束本轮
  → 用户补日志/步骤/期望 → 第二次调查与修复
  → 核实根因 → 编辑与可用验证 → 补丁及剩余实机验证事项
```

## 2. 首次分析

Agent-3沿上游线索读码，确认成功状态会解除loading，找到IPC订阅；尚不知道相机断开时服务实际发送什么。形成两个未证实假设：服务没有发送终态，或客户端收到失败状态却未处理。

用户也未说明失败后希望自动关闭窗口还是保留错误详情。此时不改码，第一轮没有patch。

每票保存的信息：

| 类别 | 本例内容 |
|---|---|
| 用户原始陈述 | 相机断开后一直校正中；来源为初始工单 |
| 已核实代码事实 | 成功终态清理loading；订阅入口与相关符号 |
| 版本与工作区 | 桌面仓基线、相关文件摘要、已有修改情况 |
| 上游调查 | Agent-2提供哪些线索、哪些已经核实 |
| 待验证假设 | 服务不发终态；客户端不处理失败终态 |
| 已查与未查范围 | 页面/状态/IPC已查，服务实现和实机消息尚缺 |
| 补充请求 | 断开前后日志、断开时机、失败后期望交互 |
| 修改状态 | 未修改，无补丁 |
| 方法与技能 | 使用了什么skill及版本、完成步骤、未完成事项 |

完整可获得会话和工具输出也保留；恢复时不要求把全部历史正文重新注入，关键证据可按引用回查。

首次报告应表达：

> 已找到桌面任务状态链路，尚缺断连时实际消息，无法区分服务未终止任务和桌面端漏处理。请补断连前后日志及期望交互。尚未修改代码。

不能把“服务源码未提供”写成已经证明缺陷一定在外部仓，也不能把没有找到原因写成不可能修复。

## 3. 首轮技能使用

- 业务skill：消息通道、日志位置、任务状态含义、设备条件。
- 系统调试skill：沿页面→状态→IPC→服务边界追踪，记录竞争假设与缺口。
- 不自动注入所有Vue/性能/浏览器技能；只有发现对应机制时再选择。

技能进度应记录为“已追踪至IPC边界，缺实际消息”，而非仅有“使用systematic-debugging”。

## 4. 用户补充与认识更新

用户第二天补充：

> 拔USB后发生。日志收到taskState=failed，错误为CAMERA_DISCONNECTED。希望保留失败窗口和错误原因、解除loading，重连后允许重试。代码没更新，上一轮也没有修改。

更新当前有效认识：

- 用户提供的日志表明本次复现服务已发失败状态；排除“本次服务没有发终态”假设。日志的来源和对应场景保留，不能无限推广到所有断连情况。
- 期望已明确，不能把自动关窗作为修复方向。
- 基线未变的陈述需要用实际文件状态核实；核实后复用既有调用链。
- 信息阻断解除，不能继续被第一轮needs_info分类永久跳过。

旧假设与旧报告保留为历史，注明为何失效；新事实不直接改写掉原始输入。

## 5. 续接或新开会话

本例同票、同基线、方向连续，可恢复指定分析会话，并显式告知新增事实和被排除假设。恢复后仍核实实际文件。

以下情况更适合新会话：换仓或显著改版、原需求理解被推翻、长历史混杂多次无效方向、会话不可得。新会话读取当前事实、相关证据、已排除项和工作区状态，并非从零重查。

会话分支适用于保留原调查并尝试替代路线；只分支对话并不自动隔离代码目录。若两条路线都编辑，需要分别管理workspace，不能同时写同一个目录。

## 6. 二次修复

Agent-3核实状态处理函数只处理成功终态，失败消息未触发清理和错误展示，形成代码与实际消息相互对应的根因证据。

向编辑阶段交接：

- 用户确认的交互期望。
- 实际失败消息与来源。
- 当前代码遗漏分支及版本。
- 修改范围、正常成功流程和订阅清理等约束。
- 可做的验证及实机条件缺口。

分析与编辑可以分会话，但不能只交接“补上失败分支”这一句。

技能随阶段重新判断：业务skill解释状态、错误展示和重试；若涉及订阅释放再使用Electron边界/生命周期方法；页面可运行才使用浏览器测试；完成前验证方法要求声明与已执行证据相符。

## 7. 候选补丁A与B

第二轮产生候选A，处理失败状态并解除loading；检查重试行为时发现新任务开始前旧错误没有清理，于是修正为候选B。

- A保留为历史，标为被B替代；B是相对本轮选定基线的完整修复。
- 不是让用户先应用A再猜如何叠B。
- B改变后，受影响检查重新执行；A的结果不能直接算作B的结果。
- 在同一工作区从A改成B可以是正常增量编辑；若放弃整个A路线，则基于记录核实并重建基线，不能连同用户改动一起盲目回退。

未来用户反馈B仍有问题时，先确认：

| B状态 | 下一步依据 |
|---|---|
| 未应用 | 可在原基线重新修正候选 |
| 已应用 | 在包含B的当前代码调查 |
| 已应用并人工修改 | 识别人工变化，再决定修正范围 |
| 已丢弃 | 不再当作当前代码的一部分 |
| 不明确 | 先核实文件，不重复应用 |

旧方案是否放弃取决于反馈推翻的内容，不统一叠加，也不统一重置。

## 8. 第二轮报告和后续入口

假设仅能执行类型检查与模拟IPC消息检查，没有相机：

> 已处理失败终态和重试前状态清理；类型检查与模拟失败消息检查通过。真实USB断连和重连尚未执行，附具体待验证步骤。

保存本轮输入版本、基线、完整B补丁、对应检查记录、使用skill及版本、实机待验项和假设变化。

后续若用户反馈实机仍无法重试，应继续核实就绪与重试条件；失败消息接收链可复用，但旧的“修改已足够”判断重新评估。用户反馈应绑定他实际验证的版本/补丁，不能默认对应最新产物。

## 9. SDK会话与业务记录的分工（2026-11-14讨论补充）

SDK会话负责对话连续性；业务记录负责当前事实、缺陷状态、证据适用范围与交付物。保留SDK会话可以减少重复组装对话历史；不需要自研另一套通用对话引擎。但业务状态不能只靠模型从长会话临时推断。

SDK session_id与缺陷ID不是一回事：一票可以有多轮尝试，一轮可能有分析/编辑/审查等多个会话；同一会话也可能承接多轮。对应关系需由应用记录，不能靠当前目录的最近会话猜测。

文件检查点可辅助撤销受跟踪工具编辑，不是仓库/运行环境完整快照；不会自动回退对话。Git基线、完整patch、实际文件与用户改动需要单独管理；分支对话也不等于分支代码。

会话正文可能含日志/代码，但只保存正文中的描述或本地路径，不足以保证原附件、报告、截图及patch跨环境可得。关键证据和产物需要持久保存并关联版本；会话用引用指向它们，不必重复复制所有内容。

配合方式的讨论顺序：先接收并保留反馈→确认它针对哪轮/哪个补丁→核实当前代码→更新事实与失效项→选择续接/分支/新会话→带入变化与有效上下文→执行→保存本轮产物和会话关联。这里是语义说明，尚未决定API和存储实现。

参考官方文档（核查日期2026-11-14，具体能力须对照实际SDK/CLI版本）：

- [会话](https://code.claude.com/docs/en/agent-sdk/sessions)：对话历史恢复、指定ID续接及分支；不保存文件系统。
- [会话外部存储](https://code.claude.com/docs/en/agent-sdk/session-storage)：跨机器/临时运行环境的会话持久化选项；不能把session ID本身视作已备份历史。
- [文件检查点](https://code.claude.com/docs/en/agent-sdk/file-checkpointing)：跟踪特定编辑工具的文件变化，回退文件与回退对话是不同操作。
